# Adaptive SQL Tutor — Technical Design

## 1. Architecture

V1 uses:

`Streamlit + Python + LLM + Tools + PostgreSQL`

High-level flow:

```text
                    User
                      │
                      ▼
              Tutor Orchestrator
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
    Learning State              LLM Tutor
          │                       │
          │                 structured action
          │                       │
          └───────────┬───────────┘
                      ▼
                 Tool Registry
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
 Learning Service  Lab Service   SQL Executor
       │              │              │
       └──────────────┼──────────────┘
                      ▼
                  PostgreSQL
               ┌──────┴──────┐
               ▼             ▼
             tutor           lab
```

No multi-agent architecture is required for V1.

## 1.1 Graphical interface

The V1 graphical interface is a local Streamlit application. It presents the
tutor conversation, diagnostic interactions, SQL editor, execution results and
the current learning state. Streamlit calls application services and does not
implement pedagogical rules or access PostgreSQL directly.

The interface is local and single-user; authentication and a separately
deployed frontend are out of scope.

---

# 2. Runtime Responsibilities

## Tutor Orchestrator

Coordinates the interaction cycle.

Responsibilities:

- load current learning state;
- call the LLM;
- validate structured output;
- execute requested tools;
- return tool results to the LLM;
- repeat until a learner-facing response is produced;
- persist relevant events.

It SHALL NOT contain pedagogical rules that belong to the tutor prompt unless deterministic behavior is explicitly required.

---

# 3. LLM Tutor

One primary LLM performs:

- intent discovery;
- PROBE;
- diagnosis;
- scenario design;
- contextual graph reasoning;
- teaching;
- exercise generation;
- evaluation;
- adaptation;
- review;
- Apply;
- Transfer Test.

The LLM does not directly access PostgreSQL.

## 3.1 Current Gemini implementation

The current implementation uses the Google AI Studio Gemini API through Google's OpenAI-compatible endpoint, using the Python `openai` SDK. The endpoint is configured with `LLM_BASE_URL` and the Google API key with `LLM_API_KEY`.

The client uses Chat Completions rather than assuming the full OpenAI Responses API. It requests JSON output, validates it as `TutorResponse`, extracts function tool calls, and passes them to the deterministic Python Tool Registry. This compatibility layer is limited: OpenAI-specific parameters and hosted tools must not be assumed to work with Gemini. Provider-specific translation remains isolated in `src/app/llm/client.py`.

All interaction with the database occurs through tools.

# 4. Tools

Initial tools:

```text
create_lab
execute_sql
inspect_lab
extend_lab
reset_lab
load_learning_state
save_learning_evidence
```

Tools SHALL expose validated input/output contracts.

Tools SHALL be deterministic whenever possible.

---

# 5. Tool Contracts

## create_lab

Purpose:

Create or replace the current `lab` schema according to a pedagogical Lab Specification.

Conceptual input:

```json
{
  "description": "E-commerce lab for Window Functions",
  "ddl": [],
  "seed_sql": []
}
```

Behavior:

1. recreate `lab`;
2. execute approved DDL;
3. populate seed data;
4. validate successful creation;
5. return current schema summary.

---

## execute_sql

Input:

```json
{
  "sql": "SELECT ..."
}
```

Output:

```json
{
  "success": true,
  "columns": [],
  "rows": [],
  "row_count": 0,
  "error": null
}
```

Actual PostgreSQL results SHALL be returned.

---

## inspect_lab

Returns:

- tables;
- columns;
- types;
- constraints;
- relevant indexes;
- optionally compact sample data.

The output should be compact enough for LLM context.

---

## extend_lab

Adds pedagogically required structures or data without recreating the entire environment.

Input MAY contain:

- DDL;
- DML;
- description/reason.

Return updated schema summary.

---

## reset_lab

Restores the current Learning Lab to its defined baseline.

Implementation MAY use stored provisioning SQL in V1.

---

## load_learning_state

Returns compact persisted learning state.

Include:

- session;
- goal;
- phase;
- concepts;
- mastery;
- confidence;
- misconceptions;
- recent relevant evidence;
- scenario summary.

Avoid returning the entire event history on every request.

---

## save_learning_evidence

Persists evidence generated by an evaluated interaction.

Input SHOULD include:

- concept;
- evidence type;
- difficulty;
- correctness;
- reasoning quality;
- attempts;
- assistance;
- raw evidence when useful.

---

# 6. LLM Structured Models

Use Pydantic models for LLM/application boundaries.

Conceptual model:

```python
from typing import Any, Literal

from pydantic import BaseModel, Field


class ToolCall(BaseModel):
    name: Literal[
        "create_lab",
        "execute_sql",
        "inspect_lab",
        "extend_lab",
        "reset_lab",
        "load_learning_state",
        "save_learning_evidence",
    ]
    arguments: dict[str, Any]


class TutorResponse(BaseModel):
    phase: Literal[
        "INTENT",
        "PROBE",
        "DIAGNOSE",
        "PLAN",
        "TEACH",
        "PRACTICE",
        "EVALUATE",
        "ADAPT",
        "REVIEW",
        "APPLY",
        "TRANSFER_TEST",
    ]

    message: str | None = None
    current_concept: str | None = None
    tool_calls: list[ToolCall] = Field(default_factory=list)
```

The exact schema MAY evolve during implementation.

The application SHALL NOT infer tool calls from prose.

---

# 7. PostgreSQL Design

Use one PostgreSQL instance.

Schemas:

```text
tutor
lab
```

## tutor schema

Application-owned.

Created through migrations.

Never dynamically redesigned by the LLM.

## lab schema

Tutor-driven.

Disposable.

Created and evolved dynamically.

# 9. Learning Scenario Representation

V1 MAY store the scenario as JSONB.

Example:

```json
{
  "topic": "Window Functions",
  "goal": "Use Window Functions in analytical SQL",
  "starting_level": "intermediate",
  "target_capabilities": [
    "partition data",
    "rank rows",
    "navigate temporal rows",
    "use window frames"
  ],
  "known_strengths": [
    "GROUP BY",
    "aggregations"
  ],
  "gaps": [
    "window semantics"
  ],
  "strategy": {
    "preferred_exercises": [
      "BUILD",
      "DEBUG"
    ]
  }
}
```

Normalization can be introduced only after actual query/use cases justify it.

---

# 10. Knowledge Graph Representation

For V1, graph relationships MAY be represented inside scenario JSON or using a minimal relational structure if implementation needs querying.

Do not introduce a graph database.

Conceptual relationship:

```text
prerequisite → concept
```

Example:

```text
row granularity
      ↓
window semantics
      ↓
PARTITION BY
      ↓
window frames
```

The graph is contextual and mutable.

---

# 11. Learning Path

Do not model the Learning Path as a permanent fixed syllabus.

Represent primarily:

```text
current
next candidates
near-future candidates
```

Example:

```json
{
  "current": "window-semantics",
  "next": [
    {
      "concept": "partition-by",
      "priority": 0.91
    },
    {
      "concept": "row-number",
      "priority": 0.72
    }
  ]
}
```

Recalculate after meaningful evidence.

---

# 12. Mastery

The LLM SHOULD generate evaluation evidence.

Python SHOULD own deterministic mastery calculation once the algorithm is defined.

For the earliest implementation, a simple weighted strategy is acceptable.

Example factors:

- correctness;
- difficulty;
- reasoning quality;
- independence;
- recency;
- repeated evidence.

Do not treat the mastery algorithm as pedagogically final.

Keep it replaceable and testable.

---

# 13. Lab Specification

Before provisioning, the tutor should produce a structured Lab Specification.

Conceptual structure:

```json
{
  "name": "window_functions_ecommerce",
  "purpose": "Practice analytical Window Functions",
  "tables": [],
  "data_requirements": [],
  "pedagogical_invariants": []
}
```

Example invariant:

```text
At least three ranking groups contain tied values.
```

Another:

```text
Relevant customers contain at least five orders on distinct dates.
```

The provisioned dataset SHOULD be validated against important invariants where practical.

---

# 14. Lab Provisioning Strategy

V1 may use LLM-generated PostgreSQL DDL/DML for the `lab` schema.

Flow:

```text
LLM
 ↓
Lab Specification
 ↓
DDL/DML
 ↓
Python Lab Provisioner
 ↓
PostgreSQL
 ↓
inspect/validate
 ↓
tool result
 ↓
LLM
```

The application should make failures visible to the LLM so it can repair lab provisioning when appropriate.

---

# 15. Executable Exercise Flow

## Tutor-provided SQL

```text
Tutor generates query
        ↓
Learner executes
        ↓
execute_sql
        ↓
PostgreSQL result
        ↓
Learner interprets
        ↓
Tutor evaluates explanation + result
```

## Learner-written SQL

```text
Tutor gives requirement
        ↓
Learner writes SQL
        ↓
execute_sql
        ↓
PostgreSQL result/error
        ↓
Tutor evaluates:
SQL + result + requirement
        ↓
Evidence
```

# 16. Adaptive Loop

Core runtime:

```text
OBSERVE
   ↓
EVALUATE
   ↓
CREATE EVIDENCE
   ↓
UPDATE LEARNER MODEL
   ↓
REASSESS SCENARIO
   ↓
REPLAN
   ↓
TEACH/PRACTICE
```

When necessary:

```text
REPLAN
   ↓
EXTEND LAB
```

The lab itself is therefore part of the adaptive system.

# 19. Testing Strategy

## Unit

Test deterministic components:

- mastery calculation;
- model validation;
- repositories;
- lab SQL execution result mapping;
- tool dispatch.

## Integration

Use real PostgreSQL.

Test:

- migrations;
- lab creation;
- DDL/DML;
- inspection;
- query execution;
- reset;
- persistence.

## Scenario Tests

Test adaptive behavior at a higher level.

Primary scenario:

`Window Functions`

At minimum create simulated learner profiles:

### Strong prerequisites

Correctly understands:

- GROUP BY;
- aggregation;
- row granularity.

Expected:

Proceed toward Window Functions.

### Weak prerequisites

Fails to understand:

- aggregation granularity;
- effect of GROUP BY.

Expected:

Introduce prerequisite remediation before Window Functions.

The two scenarios MUST result in meaningfully different learning actions.

# 20. V1 Architectural Constraints

Do not introduce multi-agent orchestration.

Do not introduce a graph database.

Do not introduce Redis.

Do not introduce a message broker.

Do not introduce cloud infrastructure.

Do not create separate PostgreSQL instances for learning labs.

Do not prematurely normalize every scenario field.

Do not create a generic plugin framework.

Optimize for proving the adaptive-learning hypothesis.

---

# 21. Future Extension Points

Not V1 requirements, but preserve reasonable replaceability for:

- alternative LLM providers;
- multiple agents;
- other SQL dialects;
- multiple learners;
- richer mastery models;
- spaced repetition scheduling;
- UI SQL editor;
- sandboxing;
- remote labs;
- benchmark/evaluation framework.

Do not implement these until required.
